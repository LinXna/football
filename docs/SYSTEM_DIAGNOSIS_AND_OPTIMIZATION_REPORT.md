## 一、 系统全链路现状与断层根因诊断

系统拥有非常丰富的数据源解析能力（YBTY 真实盘口与赔率、雷速实时统计、比赛事件、主客阵容、近期战绩、H2H 历史交锋等）。然而，在实际运行中出现了**“预测准确率低”**的现象。

### 核心断层根因：双引擎架构割裂
经过全链路代码排查，系统底层实际存在两条相互独立的计算链路：
1. **AI 深度评估链路（Node.js 端）**：
   - 实现了 6 大高级战术量化引擎（`advancedTacticalQuantitativeEngines.ts`）、主客场特异性深度挖掘（`formAndH2HDeepMining.ts`）以及泊松矩阵运算。
   - 该部分数据被打包并注入给 AI，AI 评估层能看到这些复杂特征。
2. **系统自带预测 / 基础初筛模型（Python 端）**：
   - 曾被定位为“高吞吐轻量过滤器”，使用了粗糙的线性经验公式；
   - 甚至将雷速深度特征长期标记为 `descriptive_only_not_scored`（仅做文字展示，不参与打分）；
   - 未引入去除抽水的公允期望值计算（Fair Probability），导致经常选择名义胜率看似高（如 1.25 低赔）、但长期数学期望为负（-EV）的陷阱盘口。

**本次优化的核心**：打破两端壁垒，将高阶量化数学引擎全面赋能至基础预测模型与前端串关逻辑中，实现全系统标准完全一致。

## 二、 针对用户两大核心疑问的深度技术溯源

### 疑问 1：角球 4-0 是写死的还是动态方程计算？

#### 1. 数学运算层面（100% 动态方程，绝对没有写死）
在底层量化计算中，角球**完全是根据实时抓取的双方真实角球数动态计算的**，具体数学方程如下：
- **实时角球净胜差**：$\Delta Corners = Corners_{home} - Corners_{away}$
- **角球爆发速率（每 10 分钟）**：$Velocity_{corner} = \frac{Corners_{total}}{\max(minute, 1)} \times 10$
- **边路挤压比率**：$Squeeze = \frac{Corners_{home}}{Corners_{total}}$
- **角球对泊松期望进球 $\lambda$ 的实时转化贡献**：$xG_{corner} = Corners_{total} \times 0.048$
- **实时进攻优势指数（Dominance Index）**：
  $$Dominance = 1.8 \Delta S_{target} + 0.35 \Delta S_{total} + \mathbf{0.40 \Delta Corners} + 0.04 \Delta Danger + \dots$$

系统在每次数据刷新时，无论是 `1-0`、`3-2` 还是 `6-1`，都会代入双方实际数值进行运算。

#### 2. 为什么系统里能看到“角球 4-0”？
排查发现，这是**日志文本格式化时的静态描述残留**造成的误解：
- 在 `recommend_live.py` 中，计算出动态的 `dominance` 优势指数后，日志格式化字符串被写成了：
  ```python
  # ❌ 动态计算了数值，但日志尾部写了静态示例文字：
  evidence.append(f"实时优势指数：主队{dominance:+.2f} (包含角球4-0级压制与纪律因子)")
  ```
- **解决方案**：彻底清除所有静态举例文字，全面改造为动态真实插值：
  ```python
  # ✅ 全面改为动态真实比值描述：
  evidence.append(f"实时优势指数：主队{dominance:+.2f} (角球主{home_c}-客{away_c}，纪律主{home_reds}-客{away_reds})")
  ```

### 疑问 2：为什么选 2 串、3 串时会频繁出现 2 场完全一样的比赛？

排查发现，这是由 **AI 服务端规范拦截缺失** 与 **前端内置串关算法池重叠** 双重作用导致的：

#### 1. AI 评估端（`parlay_check` 模式）缺乏组合签名去重
- 当用户请求生成多组串关时，Gemini 倾向于在所有候选比赛中挑出它认为“最稳”的 2 场核心比赛（如 Match A 和 Match B）。
- AI 在生成 Ticket 1 时使用了 `[A, B]`，在生成 Ticket 2 或 Ticket 3 时，依然将 `[A, B]` 作为核心骨架复用。
- 服务端 `parlayRecommendationNormalizer.ts` 之前只校验了每一腿赔率是否合法，**没有对整张票的比赛集合做唯一性签名校验（Signature Deduplication）**，导致重复组合被直接放行展示。

#### 2. 前端内置推荐算法（`BettingRecommendationsView.tsx`）候选池重叠
- 前端内置推荐预置了多个票据生成器：
  - `Ticket 1`（2串1 多市场价值组合）：从候选池按综合评分取前 2 名；
  - `Ticket 3`（2串1 进球大战/大小球专项）：从候选池筛选“大球”比赛取前 2 名。
- **问题爆发点**：如果当前候选池中评分最高的前两名正好都是“大球”方向，`Ticket 1` 选了它们，`Ticket 3` 又把它们选了一遍！最终卡片标题虽不同，但里面的 2 场比赛、盘口和赔率**完全一模一样**。

## 三、 五大预测痛点的系统性数学与架构重构

### 3.1 现场压制力（角球速率与禁区挤压）
- **痛点**：原模型只使用 `射正 * 0.25 + 射门 * 0.03`，完全忽略角球和禁区挤压。
- **重构方程**：
  $$\lambda_{rest} = \left( \frac{xG_{shots} + xG_{corners}}{t} \times (90 - t) \times Decay(t) + P_{trend} \right) \times Multiplier_{red}$$
  将角球 $xG_{corner}$ 与每 10 分钟角球爆发速率深度绑定至泊松剩余进球期望。

### 3.2 非线性时段与体能发力期加权
- **痛点**：线性时间衰减 `(90 - min) / 90` 无法反映足球比赛的非线性进球特征。
- **重构分段加权函数**：
  - $0'-15'$ 战术试探期：权重系数 $0.85$；
  - $16'-45'$ 常规推进期：权重系数 $1.00$；
  - $46'-55'$ 半场重整期：权重系数 $0.92$；
  - **$56'-75'$ 换人提速与核心攻坚期**：权重系数 **$1.22$**（进球高发转换期）；
  - **$76'-90'$ 体能透支与搏命攻防期**：权重系数 **$1.28$**（防守失误与破门方差最大化）。

### 3.3 纪律失衡与红牌物理乘数折算
- **痛点**：红牌只被视作文字风险，未改变数学期望。
- **重构方案**：当某队领到红牌时，对受罚方的防守失球期望施加 **$1.75x \sim 2.30x$** 的物理放大乘数，削弱其反击进球期望，并在进攻优势指数中施加 $\pm 6.5$ 的断崖式偏置。

### 3.4 历史交锋（H2H）与主客场特异性泊松先验
- **痛点**：雷速交锋和战绩数据被标记为不计分。
- **重构方案**：构建 `quantitative_prior` 模块，根据主客场场均积分（Standing PPG）、攻防效率比及历史交锋场均进球，预先推导主客队理论进球期望 $\lambda_{home\_prior}$ 与 $\lambda_{away\_prior}$，作为滚球与赛前判定的基准针（Prior Anchor）。

### 3.5 真实盘口去水与 +EV 价值门禁
- **痛点**：单纯偏向低赔，踩中庄家高抽水的负期望陷阱。
- **重构方案**：引入公允概率与正期望值（+EV）过滤算法：
  $$Fair\ Prob = \frac{1 / Odds}{\sum (1 / Odds_i)}$$
  $$EV = (P_{model} \times Odds) - 1.0$$
  $$Value\ Edge = (P_{model} - Fair\ Prob) \times 100\%$$
  **硬性门禁**：仅当 $EV > 0$ 且 $Value\ Edge \ge +2.5\%$ 时，系统才允许输出推荐。

## 四、 串关防重复与核心腿相关性风控重构方案

针对串关重复出现的严重 Bug，确立并实施以下硬性风控规则：

```
┌─────────────────────────────────────────────────────────────┐
│                    候选比赛与方向池 (A/B 级)                  │
└──────────────────────────────┬──────────────────────────────┘
                               │
            ┌──────────────────┴──────────────────┐
            ▼                                     ▼
   【组合签名去重 (Deduplication)】       【重叠率熔断 (Overlap Gate)】
   两张票的比赛/方向集合完全相同 ➔         同为 2串1：允许重叠场次 = 0 场
   直接剔除重复票，强制换用独立腿         2串1 与 3串1：允许重叠场次 ≤ 1 场
            │                                     │
            └──────────────────┬──────────────────┘
                               ▼
               【专项票互斥生成 (Exclusive Selection)】
               Ticket 3 强制排除 Ticket 1/2 已选比赛，
               确保每一张串关代表独立的战术逻辑！
```

1. **组合签名去重（Ticket Signature Hash）**：
   - 将每张票内的比赛 ID + 玩法方向生成唯一排序签名；
   - 跨票比对，若两张票的签名完全一致，第二张直接判为无效重复票并拦截。
2. **重叠率硬性熔断（Max Overlap Gate）**：
   - **两张 2串1 票之间**：允许重叠场次为 **0 场**（完全独立对冲）；
   - **2串1 与 3串1 票之间**：允许重叠核心腿最多 **1 场**，严禁使用相同 2 场核心腿作为骨架。
3. **前端专项票互斥生成**：
   - 进球大战专项票（Ticket 3）在筛选候选时，强制排除已被综合价值票（Ticket 1）占用的比赛，避免同一比赛既出现在价值组合又出现在大小球专项中。

## 六、 战术量化引擎 v2.0 升级与数据真实性治理专项报告

### 1. 阵型战术克制与空间博弈精算体系（Tactical Clash v2.0）
- **核心升级**：建立包含 12 大主流阵型（`4-3-3`、`4-2-3-1`、`4-4-2`、`3-5-2`、`3-4-2-1`、`5-3-2` 等）的精算库，全景量化中场中路绞杀、边路宽度压制、肋部半空间攻防、高位压迫及低位大巴抗性。

- **交互与可视化**：新增 `FormationClashModal.tsx`（足球阵型战术克制与空间博弈精算交互面板与阵型全息百科）。

### 2. 严禁盲目兜底：彻底清除“缺省回填 4-2-3-1”
- **根因**：部分小联赛（如玻利维亚杯、阿根廷后备队）未提供官方首发阵型，系统原先存在多处 `|| '4-2-3-1'` 默认回填，导致在无阵型数据时盲目计算克制。
- **治理举措**：
  1. 引入统一 `UNKNOWN` 阵型类型与 `is_available: false` 标记；
  2. 当任一队缺少阵型数据时，`evaluateFormationClash` 自动触发主动关闭策略，返回 `NO_FORMATION_DATA` 与中立置信度，不再产生误导性战术克制结论；
  3. 全链路（`server/services/formationTacticalEngine.ts`、`src/lib/formationTacticalEngine.ts`、`src/utils/dataAdapter.ts`、`server/services/canonicalMatchModel.ts` 等）全面移除硬编码兜底。

### 3. 全场事件流与时序波形事件去重修复
- **根因**：`AttackMomentumTimelineWidget.tsx` 在事件去重时仅依据 `minute` 和 `type`，导致同一分钟内发生多个角球或黄牌时，后续角球（如谢周三VS布拉德福德城第3个角球）被误判为重复事件而吞掉。
- **修复**：将 `cornerNum` 和 `cardNum` 纳入 `dedupeKey`，确保时序流中所有角球、红黄牌、进球完整渲染。

### 4. 统计面板与文字关键攻防事件差异审计
- **审计结论**：面板统计（如射门 3/8-3/6）与文字直播中的关键攻防事件（7次射正）差异源自雷速上游数据源的分离记录（统计面板为官方接口事实数据，文字事件流由人工/AI文字流打点），非本地代码合并错误。系统已遵循**“不强行强绑定两者关系”**的原则，真实呈现数据本身。

## 七、 2026-08-22 全量量化算法精修、孤立特征激活与后端拓扑治理专项

### 1. 亚洲让球盘连续泊松积分重构 (`computeAsianHandicapProb`)
- **历史缺陷**：`server/services/quantitativeFeatures.ts` 原先对全场与半场让球盘采用离散阶梯估值（固定赋予 `42% / 50% / 60%`），导致深盘与浅盘的物理胜率无差异。
- **治理举措**：构建专用的 `computeAsianHandicapProb` 函数，在 $7 \times 7$ 独立泊松得分矩阵上对让球线进行连续积分，严格计入赢半（+0.25 盘口权益 50% 转化）、输半（-0.25 盘口权益 25% 留存）与走盘（0 盘口 50% 权益计入），产生平滑且真实的物理胜率与 Edge 差值。

### 2. 半场期望衰减函数消除临界点跳变 (Half-time Smooth Decay)
- **历史缺陷**：半场进球期望折算在 44~45 分钟时段分母接近 0，产生微小时段跳变。
- **治理举措**：平滑化衰减公式，重构为 $\max(0.05, \text{Goal} + \lambda_{\text{rest}} \times \frac{\max(0, 45 - t)}{\max(1, 90 - t)})$，确保半场临界阶段数值自然平滑。

### 3. 角球让球盘攻防倾角融合 (Corner Spread Blended Projection)
- **历史缺陷**：角球让球盘仅依赖历史角球比例，对单边高压围攻但角球暂时落后的场次反应迟钝。
- **治理举措**：将前场危险进攻压迫倾角 Field Tilt（40% 权重）与角球比例（60% 权重）进行非对称加权融合，使角球让球盘更契合场上真实攻防压迫态势。

### 4. 激活 5 大雷速休眠维度 (Dormant Features Activation)
- **历史缺陷**：进球时段分布、交锋历史、近况、积分榜、盘路走势仅展示在前端，后端物理推演未利用。
- **治理举措**：
  1. 将 5 大维度完整打通至 `CanonicalMatchData.context` 标准数据契约中；
  2. 在 $t \ge 60'$ 推演中引入 `goal_distribution` 特征：若球队在 76-90+ 分钟有历史进球偏好（$\ge 3$ 球），自动赋予破门动能 $1.10\times$ 爆发补偿。

### 5. 后端依赖拓扑治理与 0 孤立文件达成 (Zero Orphan Files)
- **治理举措**：将遗留的 `server/services/batchSupplementTypes.ts` 与 `server/services/geminiEvaluationTypes.ts` 重新接入对应服务（`batchSupplementService.ts`、`geminiEvaluationService.ts`），实现 `server/` 目录下全部 46 个文件 100% 导入运行，消除孤立废弃代码。
